# Fresh-context workflow validation

A repaired example demonstrates that the repair works. To evaluate a reusable workflow, also test whether a new agent applies it to an unseen task.

1. Freeze a package snapshot and record its hash, requested model, and effort.
2. Preserve existing outputs as a baseline. Create a new empty work directory; do not delete unrelated user work.
3. Supply the user's raw brief/data, current user-authored clarifications/preferences, and the plugin package. Preserve each clarification's source and scope. For from-scratch cases, do not supply starter implementation, previous screenshots, agent-proposed fixes, or expected answers. A legitimate user requirement is not evaluator leakage merely because it was stated after the original brief.
4. Dispatch a fresh context with the caller's selected model configuration. Keep evaluator criteria and previous conversation outside its supplied context. This is logical separation unless an actual OS sandbox enforces read access.
5. Observe the chosen workflow, code, rendered product, failures, and verification claims. Review actual outcomes independently, using criteria derived from the brief and the workflow's intended behavior.
6. Separate handoff omissions, reference-discovery failures, unsuitable decisions despite reading a source, implementation failure, unsupported verification claims, and missing tool access. Do not promote a claimed pass without supporting evidence. A rule that was present but not applied needs a decision/verification-flow correction, not automatically another copy of the same rule.
7. If an issue is found, fix the narrow general decision criterion, recheck the affected case, and use another fresh task when a generalization claim needs evidence. Do not accumulate one universal prohibition per example.

Use tasks that exercise different reference needs: a source lookup, a custom connection, a default choice, or general mode with no authored source. Domain outcome criteria belong to the selected source and the user's task. Do not copy a role's review checklist into this client or require every role source for a test.

Finite cases provide observed evidence, not proof of universal compliance. Report task coverage and limits. A sample that ships inside the plugin is a reference, not a held-out answer; use a different task when testing transfer.

Evaluation inputs should represent the task's actual scope, not hide extra acceptance rules in the evaluator. If an operational bound or format dialect is unspecified, treat that as an interpretation or source gap unless an adopted contract settles it. Explain why an adversarial input matters and distinguish a technical boundary from demonstrated operational impact. Maintainer evaluations do not establish a required model, time budget, or fixed sequence for ordinary users; those belong to the caller and the ongoing task.

## Consumer-owned evaluation inputs

The public repository supplies this method and generic preparation tooling, not a catalogue of project cases. Keep task briefs, input data, rubrics, generated apps, and raw results in the consuming project or ignored `.local/`. Use `scripts/prepare_eval.py --input <raw-input-directory> --output <new-project-directory> [--context <user-context-directory>]`. Both supplied directories have a README describing their purpose; the context directory records user clarifications with source/scope. Keep evaluator criteria separate. The preparer preserves original input, the plugin, and the execution harness with hashes outside the editable project so a later implementation document cannot silently replace the expected outcome or execution contract.

For CLI execution with independent review, use `scripts/run_eval.py --input <raw-input-directory> [--context <user-context-directory>] --review`. The runner inherits the caller's CLI model configuration by default; optional `--model` and `--reasoning-effort` override only the supplied settings for implementation and review. It records explicit selections or configuration inheritance without guessing the serving model. The runner freezes the artifact as soon as the model process returns, including executable permissions. Later project edits do not replace that snapshot. The reviewer gets preserved input, frozen plugin and harness, and that artifact in a separate context. Review decisions use the user input and any already-selected source guidance. The runner supplies paths and the machine contract without bundling a domain review capability. It writes observations/findings/unverified scope with reproduction steps and evidence. It must not repair the first output. `scripts/review_eval.py --project <prepared-project> --prepare-only` supports dispatch through another authorized harness. Without a runner completion snapshot, this is explicitly a manual capture of the current artifact, not proof of an earlier model result; after that run, use `--check-only <review-directory>` to validate source/evidence ownership and captured execution provenance. The helper snapshots local evaluation material, not organizational context, and excludes dependency/environment directories listed in its baseline.

Execution success, a contract-verified review, and product acceptance are different claims. The report checker detects missing evidence, invalid paths, altered review material, repaired execution copies, changed test inputs, and evidence not captured by the declared execution; it cannot establish completeness, truthful interpretation, visual quality, or user acceptance. Inspect its concrete observations. This logical isolation is not an OS sandbox. The reference protocol remains metadata-only; runtime evaluation and its evidence belong to the execution environment.

Review sources declare their owner: `input` for preserved user requirements, `package` for the frozen reference client contract, and `reference` for an independently owned source read through a review-local trace and receipt. A reference observation retains its read-time digest; it is not a claim that the remote source stayed unchanged. Keep a procedural finding distinct from a product defect; do not cite a convenient user sentence as if it defined the harness's rules. External-reference applicability still needs human/agent review and cannot be established by file-path validation.

After the run, compare the reference/source trace with observed tool use. Trace validity proves only that recorded transitions follow the protocol. Inspect the actual action region and feedback lifetime in addition to geometry, focus, and data preservation. Domain guidance belongs in its selected source; project-specific expected values and tests stay with the project.

## Captured execution

The prepared review's `contract.json` points to its frozen `evaluation_execution.py`. Use that tool with `--review <review-directory> -- <argument-vector>` to run a check from an unchanged runtime copy. A test script can live in the review workspace and launch the product, drive a browser, or call a CLI. Declare generated screenshots/data at new, nonexistent paths using repeated `--evidence evidence/<file>` and test inputs using `--test-input <file>`. File arguments within the review workspace are captured automatically.

The tool records the command, source file bytes and executable permissions before/after, test-input hashes, output hashes and exit/timeout status. Put generated data, build results, logs and mutable state outside `runtime/`; changes or additions to the first artifact invalidate automatic execution provenance. Dependency/environment directories are excluded explicitly, so this is application-source integrity rather than whole-machine attestation.

Report format 2 separates `runtime`, `inspection`, and `scope`. Runtime observations/findings reference the captured execution ID and its evidence; static inspection cannot establish runtime behavior. A timed-out run can support a finding about the timeout, not a completed outcome. Historical formats stay with their originating harness.

Execution records are written inside `review/.harness/executions/`, within the actual workspace-write boundary. The tool owns that directory by workflow convention; the reviewer must not edit records manually. This is not a distinct OS identity or tamper-proof evidence service. The protected baseline remains outside the review workspace.

Captures within one review workspace are serialized because they share a runtime tree and evidence paths. Different review workspaces can execute independently. A reused evidence path is rejected even when requests arrive concurrently. Every execution also belongs to a unique review identity; copying another review's record does not transfer its provenance.

To inspect an existing completion with a revised execution harness, explicitly supply `--harness <harness-source-directory>` with `--prepare-only`. The original dispatch harness stays preserved, and the selected reviewer harness is frozen separately with its own hashes. This does not rewrite the original execution history or claim that the implementer used the newer harness.
