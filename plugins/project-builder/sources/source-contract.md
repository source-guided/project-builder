# Source participation contract v1

This is the common boundary for sources connected to Project Builder. It governs discovery and exposure, not a domain's creation methodology. It applies whether the caller selects default guidance, custom guidance or the AI's general approach.

A source owns its instructions, internal capabilities, domain criteria, examples and checks. Its entry index exposes navigation metadata only. A source-local skill is reached through a reference and applied only in that context. It is not copied into a global `skills/` directory, exported by a plugin manifest, or registered as an automatic host trigger. No source may install another source as a hidden prerequisite. Cross-source needs return to the consuming project's connection choices.

Repository-backed sources declare `source.json`: format 1, a source ID and version, role, exposure `source-only`, contract `project-builder.source/v1`, an entry index and a list of internal `capabilities/.../SKILL.md` paths. This manifest is a source of ownership/version information; those values are not duplicated into discovery records. `source-files.json` lists the source's reviewed public files. DB, Confluence and other hosts provide equivalent entry/ownership information through their authorized adapter; a Git repository is not mandatory.

Use reference access `relative` for a source-owned path that must work in both a local checkout and a hosted HTTP index. The reference client resolves it using the current index transport. Local paths stay within the source in source-package validation; hosted connectors keep their own access controls. Absolute web and opaque connector bindings remain available for other sources.

## Organization of authored material

When creating or extending a source or project knowledge collection, organize its actual content by stable domain or responsibility and expose those areas through a navigable reference hierarchy. This applies to stakeholder questions and answers, requirements, specifications, decisions and verification evidence as well as reusable instructions. First identify the existing owner area; place new material there or create a meaningful owner area when none exists. Keep repository-wide entry and administrative material at the root. Do not accumulate unrelated substantive Markdown files at the root, flatten every leaf into one reference index, or merely move the same undifferentiated collection under a single `docs/` or `sources/` folder.

Each meaningful area has an entry that leads to its relevant subareas or source documents. In a filesystem source, put an area's reference entry inside its own directory, such as `references/<area>/index.json`, and its body documents under their owner directory. Represent real subareas with further directories; do not keep all area indexes as sibling JSON files directly under `references/`. Reference indexes hold navigation metadata; the referenced owner locations hold the content. Horizontal links connect related areas without copying their bodies. A single focused area can have a small leaf index; split where responsibility or the reader's task changes, not to meet an arbitrary depth or file-count quota. Do not create empty branches or require particular domain names. For remote stores and document services, use the equivalent owner/group and linked-entry structure rather than imposing filesystem paths.

Apply the same split-or-keep decision recursively inside each affected area, not only at the root. Questions, specifications and evidence may be peer documents when they describe one coherent responsibility and are normally read or changed together. When an area contains independently governed policies or workflows with distinct inputs, state transitions, owners or reasons to change, give those subresponsibilities their own areas and keep each one's questions, specification and evidence together. Repeated independent subjects across several document sections are a signal to inspect ownership, not an automatic file-count rule. Do not merely reproduce another broad `questions.md` / `specification.md` / `verification.md` collection at every level.

Different branches can stop at different depths. A parent may retain a shared contract or overview while its independent children own their detail; children refer to that shared source instead of copying it. Stop splitting when the remaining documents serve one coherent reader task and further separation would scatter a single policy or decision across artificial fragments. Revisit this decision when new material changes an affected area's responsibility, while preserving unrelated stable areas.

Before completion, verify that a reader can enter an area and find its questions, governing specification and available evidence without opening every document. Check both the content locations and the reference routes; a nested index over a flat pile of owner documents does not satisfy this requirement. Preserve one authoritative location for shared records and link affected areas to it. Detailed authoring methods and domain-specific review criteria remain with the selected owner sources. General mode does not waive this organization contract.

## Connection and storage boundaries

The common plugin distributes only its reference entry capability, connection tools, participation rules and optional default metadata. It must work without any default-source body. Default roots are not fetched on installation or while listing suggestions. User source selection records intent and binding, not copied skill bodies or account credentials.

The reference index format is independent of its storage. A consumer may keep both indexes and connection choices in files, SQLite, HTTP storage, GitHub, Supabase, S3, Confluence or a host-provided adapter. A storage profile identifies a driver and destination; credential fields identify host environment variables, not secret values. The store's revision provides conditional writes so one user's stale update cannot overwrite another's work. An unavailable revision, access denial or conflict is reported rather than downgraded to an unconditional write or local fallback.

Personal, project and organization sharing is enforced by the selected service's account and resource permissions. Sharing a reference index does not grant access to its target sources. A shared index cannot implicitly authorize local file access or another configured store profile. Receipts may also use any selected document store. Each trace retains one explicit access-context scope; a team shares the storage and readable records, not an implied common authenticated identity. Scope labels do not grant access or authenticate a person.

Receipt writes preserve session event validation and use conditional revisions when remote. Independent append operations may merge after a confirmed version change; duplicate outcomes and context changes are rejected. Access failures, uncertain write outcomes, and unchanged-revision rejections are not retried as successful writes or redirected to a local log. Exporting a JSONL snapshot is explicit and does not move the authoritative trace or claim the source has stayed current.

Source maintainers keep their own domain and authoring rules. When authoring guidance is absent, the caller chooses default, custom or general mode; selecting a methodology never waives this participation contract. Source content changes trigger a review of affected discovery metadata. Contract checks verify package boundaries and references, while domain checks remain with the source owner.
